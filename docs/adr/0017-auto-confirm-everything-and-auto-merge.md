# ADR-0017 — 所有来源都自动确认，每日数据 PR 自己合并并上线

日期：2026-11-17。状态：采纳并实现。起因：用户问“Kajimoto 今天公布的海外钢琴家公演能不能及时读到”。实际查到：Kajimoto 官网当时列 16 场，线上只有 15 场，多出来的是《SIR ANDRÁS SCHIFF PIANO RECITAL 2026》（2027-02-10）。我们的每日采集能读到它，但上不了线，原因有两个：主办方（Japan Arts、KAJIMOTO、神奈川艺术协会）按 ADR-0008 从不自动确认，只能等人在本地确认，而云端没有确认界面；数据 PR 也要等人合并（#24 从 11 月 15 日起一直开着）。用户的决定：**“都改成自动确认，每天读一次并且自动合并就好”**。

这条决定推翻了 ADR-0008 的两处：“主办方的节目不自动确认”和“数据 PR 由人合并”。

## 决定

| 问题 | 决定 |
|---|---|
| 哪些来源自动确认 | 六个乐团官网（NHK 交响乐团、都响、东响、日本爱乐、新日本爱乐、读响）**加** Japan Arts、KAJIMOTO、神奈川艺术协会。仍然不自动确认：暂缓的东京爱乐（不读）、海外线索（不是演出）。见 `autoconfirm.AUTO_SOURCES` |
| 类别闸门 | 去掉。以前只确认 `domestic_orchestra`；四个类别（国内乐团、海外乐团来日、钢琴独奏会、其他）都是站点的正式类别，主办方的节目大多不是国内乐团 |
| 其余检查原样保留 | 每场都有具体日期、会场、都道府县（`confirmable`）；有疑似重复（同一天、会场相近的另一来源）→ 留给人；早先曾从来源消失过场次 → 留给人；`confirm_stored` 自己的检查（重复决定、过去的场次、校验）；防洪（一次符合条件的超过 120 场就一场都不确认，任务变红）；每日运行只确认**本次首次看到**的候选 |
| 数据 PR | 每天读一次不变（日本时间 04:23 的定时，实际在 8:00～11:30 开始）。闸门（`cloud_publish.py`：新文件的演出数少于已发布的 90%、图片比已发布的少、一次新增超过 150 场；站点试构建；**新增：用新数据跑完整测试**）都在推送之前；全部通过后，任务自己合并数据 PR，并用 `gh workflow run deploy.yml --ref main` 启动部署，等部署成功才算这次运行成功 |
| 为什么要自己启动部署 | 用任务自己的令牌合并，不会触发 `deploy.yml` 的 `push` 触发器；`workflow_dispatch` 例外，所以工作流加了 `actions: write`，合并后显式启动部署 |
| 失败时 | 任何一道闸门或测试不过：不保存数据库、不推送、不合并，任务变红（GitHub 发邮件）。**数据库是在合并之前保存的**：如果合并或部署失败，数据库里已经确认的场次不会丢，第二天的导出仍然带着它们。合并失败（比如合并前 main 上的 `site-data/concerts.json` 被改了）：PR 留着，任务变红。部署失败：任务变红 |
| 部署被取消 | 同一时刻有人往 main 推送，`deploy.yml` 的并发组会取消其中一个部署；两个都构建同一个 main，所以任务看到“被取消”时去看更新的那个，不算失败 |
| 关闭开关 | 仓库变量 `AUTO_MERGE = false`：数据 PR 照常开，但不自己合并（和以前一样等人）。仓库变量 `AUTO_CONFIRM_PRESENTERS = false`：三家主办方又留给人（`auto-confirm --no-presenters`）。两个开关不用改代码，在 GitHub 仓库的 Settings → Variables 里设置 |
| 事后抽查 | 任务摘要的“自动确认”一节列出本次上线的每一场（来源 + 标题），主办方的单独标出【主办方】，因为它们上线前没有人看过 |
| 老候选 | 今天已存在的主办方候选是早先的运行首次看到的，每日运行的“只确认本次首次看到”会把它们当成“更早的候选”，永远不处理。一次性用手动开关 `confirm_older`：先 `apply=false` 只报告（数量和标题），再 `apply=true` 确认一次。防洪 120 照样适用，超过就一场都不确认，不会悄悄调高上限 |
| #24 | 数据 PR 是固定分支 `data/auto-refresh`、每次强制推送、只会有一个开着的 PR，所以下一次运行会更新并合并 #24 本身，不会另开 |

## 风险和限制

- **主办方的节目现在不经人看就上线。** 它们由 `parsers.py` 读出来，如果某个主办方网站改版导致解析错位，防洪（120）、新增上限（150）、“已发布的 90%”和测试只能挡住数量异常或数据结构错误的情况，挡不住“数量正常但字段读错”的情况。所以任务摘要列出每一场、开关可以随时关；`confirmable` 要求日期 / 会场 / 都道府县齐全，有疑似重复的仍然留给人。
- 留给人的节目（疑似重复、缺字段、曾经消失）仍然没有地方处理（云端没有确认界面），会一直留着；没有变。
- KAJIMOTO 的使用政策在 `docs/reports/P0_SOURCE_SPIKE.md` 里仍标为“未确认”；每日采集本来就在读它（每天一次，2 秒间隔），这次没有增加请求量。
- 海外巡演线索（オケミン）仍然只能手动读，不在每日任务里，这次没改。（同一天稍后被 [ADR-0018](0018-tour-leads-in-the-daily-run.md) 取代：线索也进每日任务并自动上线。）
- 运行时间：同步约 18.5 分钟 + 测试约 1 分钟 + 部署约 2～3 分钟，远小于 60 分钟的任务上限。

## 测试

`tests/test_autoconfirm.py`：主办方现在符合条件、`tpo` 仍在范围外、三家主办方都在范围内、`presenters=False`（开关）把它们拿出去、类别不再是闸门、主办方和乐团官网列同一场仍按“疑似重复”留给人、`went_live` 列出上线的场次、CLI 的 `--no-presenters`、摘要里标出【主办方】。`tests/test_workflows.py`：步骤顺序（比较 → 构建 → 测试 → 保存数据库 → 推送 PR → 合并并部署）、测试步骤用新数据且不留改动、合并步骤有同样的条件加 `AUTO_MERGE` 开关、`gh pr merge` 重试、`gh workflow run deploy.yml`、`gh run watch --exit-status`、被取消的处理、`actions: write`、主办方开关只加一个标志。
