# ADR-0021 — 读响 2027-28 乐季：PDF 没有文字层，改用人工转录的数据文件

日期：2026-11-20。状态：采纳并实现。起因：用户看到乐季页里读响的 2027-28 是空的，而官网已经有节目单 PDF（“读响的2728乐季明明有pdf了为什么没有显示公演”），并回答“要补”。

## 问题

- 每日同步读响只读官网日历 `cal.php`，它只到一个财年的末尾（2027-03）。2027-28 的曲目只在一份 PDF 里，乐季页里它只是个链接。ADR-0020 当时定的范围是“不新增采集”，所以页面写“暂无节目”。
- 这份〈速報版〉PDF（`https://yomikyo.or.jp/2026/11/2027-28web.pdf`，6 页，3.5 MB）**没有文字层**：`pypdf` 每页抽出 0 个字，字都是轮廓图形。ADR-0009 的“按页面坐标读文字”没有东西可读；仓库和运行环境里也没有 OCR。

## 决定

| 问题 | 决定 |
|---|---|
| 怎么拿到内容 | 看 6 页图片逐张转录，写进 `src/classical_radar/season_posters/yomikyo-2027-28.json`（打进包里；目录不叫 `data/`，因为 `.gitignore` 把所有叫 `data` 的目录都忽略了）：41 个节目、51 场（定期 10、名曲 10、土曜/日曜マチネー 10 个节目各两天、横浜マチネー 8、大阪定期 3）。文件头记着 PDF 地址、sha256、版本（速報版）和转录日期 |
| 怎么防抄错 | 加载时自检（`yomikyo_poster.load`），任何一条不符整份拒收：每个日期的星期必须等于卡片上印的星期；系列和编号唯一；日期在乐季内；会场必须有都道府县；角色必须是已知的；每场恰好一个指挥；每首曲目写成“作曲家：作品”。转录后另有两个子代理各自对着图片逐字核对：查出 1 处错字（「スターウォーズ」中间没有“・”，已改）和 1 处看不清的 Ⅱ/II（入库时统一成同一个写法，无影响） |
| 入库成什么样 | 每场一条 `concert`，标题照官网写法：“第296回土曜マチネーシリーズ”和“第296回日曜マチネーシリーズ”是两条（官网日历也是两条）。这样乐季页的系列规则（`SERIES.yomikyo`）认得出，官网出来后也能一对一接管。身份地址 `…/2027-28web.pdf?program=<系列>-<编号>`，卡片上的“官网”链接就是 PDF 本身 |
| 曲目和演出者 | 走已有的 `parse_programme` / `build_artists`，**不动 `works.py`**。`works.py` 的独奏角色表不认箏和尺八，所以演出者的类别用本模块自己的表（指挥、合唱、其余算独奏）。“ムソルグスキー（ラヴェル編）：…”的编曲者挪到作品名后面，让左边只剩作曲家，作曲家才能对上 |
| 官网列出之后 | 同一场原地迁移：同一行 `concert`，只把 `identity_key` 改成官网页面，收藏和提醒不丢，也不出现第二张卡片（和 ADR-0009 同一个思路，`sync._yomikyo_poster`）。**对应规则**（`match_official`）：先按官网标题里的“第 N 回＋系列”对，日期不同也认（节目可能改期）；官网标题没有编号时，才用“同一天、同一时间、同一会场”，而且必须恰好一场。同一天别的公演（特别演奏会、巡演）既没有编号也对不上时间会场，不会被误认。多于一场符合时只记警告，不合并。官网日期不在 2027-04-01 到 2028-03-31 之间的演出一律不算（旧乐季的同编号演出不会被当成它）。**迁移会留一条记录**：一条 `change_event`（`identity_key`，备注 `poster programme moved onto its official page`），之后无论官网的标题怎么改、哪天日历里暂时少了这一条，海报里的同一回都不会再入库成第二张卡片；`monitor.report` 不把这条算作官网的改动（`identity_key` 列入 `HUMAN_FIELDS`） |
| PDF 被换了 | 每天下载一次 PDF（走原有 `Reader`，≤5 MB），和文件头的 sha256 比。内容变了或 404 → 一条警告（每日运行变红，库里的节目保留）；其他取不到的情况（网络抖动、5xx）只在结果里记一笔，不变红。读响的正式版多半换新地址，所以 404 也算警告 |
| 孤儿 | 库里有 `?program=` 的读响卡片、转录文件里却没有（改过系列或编号）→ 警告，不会静默留下 |
| 失败怎么处理 | 这一步捕获所有异常，只记一条警告，官网日历照常入库（同 ADR-0009） |
| 确认方式 | 与其他乐团相同，自动确认（ADR-0017）。一次 51 场，低于“洪水闸”的 120。大阪的 3 场入库，页面只显示首都圈 |

## 验证

- 51 场的星期全部等于 PDF 印的星期（脚本核对）。
- PDF 印的会员发售日（年间 2027-01-09、上期 2027-01-11、大阪 2027-02-27）与 `memberships.js` 里读响那一块一致。
- 同一天别的公演、官网改期、多于一场符合、地址被占、PDF 被换/404/取不到、转录文件有错，都有测试（`tests/test_yomikyo_poster.py`）；把对应规则换成“只按日期”，两个相关测试会失败。

## 已知限制

- 这是〈速報版〉：PDF 自己写着曲目、出演者以官网最新为准，之后可能调整。正式版出来时需要重新转录；文件被替换或下线会有警告，但换了新地址的正式版程序不会自己发现。
- 133 首曲目里有 16 首的作曲家不在 `works.py` 的别名表里（イアン・ベル、サミー・ムーサ、ソッリマ、ニューマン、ノイヴィルト、フランセ、フンパーディンク、ブルッフ、ライネッケ、三木 稔），所以没有内部作曲家编号（`composer_key`）。这不影响显示：乐季页的名单和“作曲家”页都会按名字归并，这些作曲家照样有自己的页面（2026-11-20 在预览站上逐一打开核对过）。缺的只是两样：通用作品号不能把同一首合并成一条（ブルッフ页里同一首小提琴协奏曲分成了两条）；人工核对过的 Apple Music 按钮只有ブルッフ、フンパーディンク有。补编号要动 `works.py`，代价是：已上线的 4 位作曲家（ブルッフ、フンパーディンク、ライネッケ、フランセ）的页面网址会变，已上线的 9 场演出的详情页会冒出“近期有重要变更”（同步看到曲目编号变了，按“页面改了曲目”记一笔）。ニューマン（Alfred / Thomas / Randy）和ノイヴィルト（Olga / Gösta）还有重名，表的原则是“不猜人”，不能只凭姓氏补。所以这次没做。
- 土曜和日曜是两张卡片，收藏和提醒各一份（和官网一致）。如果官网将来把同一个节目的土曜和日曜放在同一个页面地址下，日曜那张会每天报一条“地址已被占用”的警告（不会合并，也不会丢），要人来看。
- 迁移记录存在 `change_event` 里。云端数据库如果从站点数据重建（`restore-site`），这条记录会丢，只剩“按标题里的第 N 回认”这一层保险；标题也改掉的话，官网那一条缺席的那天会冒出第二张卡片。
- 节目搬到官网页面之后，库里已有这一回的官网卡片（按“第 N 回＋系列”认），海报里的同一回不会再入库；官网某天的日历暂时少了这一条，也不会冒出第二张卡片。
- アンサンブル・シリーズ 不在这份 PDF 里（海报写“决まり次第发表”）。
- 官网上线后标题既没有“第 N 回”、日期时间会场也对不上，会出现两张卡片；极少见，走“疑似重复”的人工复核。
