# ADR-0018 — 海外巡演线索（オケミン！）也进每日任务，读完自动上线

日期：2026-11-17。状态：采纳并实现。起因：ADR-0017 把九个官方来源改成自动确认、每天读一次、数据 PR 自己合并之后，用户接着说：**“海外巡演线索（オケミン）也改成自动上线”**。

这条决定推翻了三处旧说法：ADR-0007 的“`leads-sync` 手动，没有定时器、`leads.json` 随 PR 审阅”，ADR-0008 的“海外线索不在这个工作流里”，ADR-0017 的“海外巡演线索仍然只能手动读”。

## 怎么理解“自动上线”

只改**怎么更新**，不改**线索是什么**。线索仍然是单独的一份列表（`site-data/leads.json`），仍然标“第三方整理，未核实”、署名“オケミン！”、官方已有同乐团同日期的演出时让位（`covered_by`），仍然不进日历、搜索、提醒，也仍然不会被当成官方演出确认（`autoconfirm` 从来不碰线索）。没有把线索升级成官方演出。

## 决定

| 问题 | 决定 |
|---|---|
| 谁来读 | 每日任务（`daily-refresh.yml`，每天日本时间 04:23 定时，实际 8:00～11:30 开始）在“自动确认”之后、“与已发布数据比较”之前新增一步：`leads-sync`，再 `leads-export` 到 `new-leads.json`。和官方来源一样礼貌：先读 robots.txt、每个请求间隔 2 秒、一次最多 80 个请求、401/403/429 立即停止、只读 okemin.com |
| 读多少 | 文章重读间隔从 3 天改成 **7 天**（`ARTICLE_REFRESH_DAYS`）：个人站点没有声明使用政策，每天只读 robots.txt 和两个年度列表页（3 个请求），再加上到期的文章。平均约 10 个请求/天；但第一次（云端数据库里还没有线索）一次读完全部约 46 个请求（不到两分钟），这批文章之后每 7 天又会同一天到期：连续六天约 3 个请求，第七天约 45 个，仍在每次最多 80 个请求的上限之内 |
| 读哪几年 | 默认“今年和明年”改按**日本时间**算（`default_lead_years`）。每日任务在 19:23 UTC 开始，12 月 31 日这一刻日本已经是 1 月 1 日 |
| 明年的页面还没建 | 每年 1 月“明年”往后挪一年，オケミン！可能还没有那一页（404）。第一个年份之后的年份遇到 404，且这一年**从来没读过**（`lead_page_read` 里没有记录），就跳过（记在 `not_published`，每日摘要的“海外乐团线索”一节会显示，不记为已读，所以不会让那一年的线索消失），继续读文章，不算中止。**读过的年份页突然 404**（被站长撤了或搬走了）、第一个年份 404、任何一页“200 但没有乐团块”（版面改了），仍然中止并报告：否则那一年的旧线索会一直挂着、没有结束 |
| 谁判断能不能上线 | `scripts/cloud_publish.py` 多收 `--leads-old site-data/leads.json --leads-new new-leads.json`。比较按 `lead_id`，忽略文件的 `as_of`、`read_at` 和每条线索的 `last_changed_at`（它只在事实变化时才动）。线索自己的闸门：新文件保留至少 **70%** 的已发布线索；一次新增不超过 **60** 条；结构合法（有 `lead_id`（`lead-…`）和 `orchestra_name`、`lead_id` 不重复）；新文件必须存在且能读 |
| 闸门没过 | **只扣下线索**：已发布的 `leads.json` 保持不变，演出照常发布；原因写在 PR 正文和 `publish.json` 的 `leads_problems` 里，每日任务在最后（演出已经上线之后）变红、GitHub 发邮件。反过来，**演出的闸门没过（退出码 3）时整个任务在那里停下，线索当然也不发**，和以前一样 |
| 怎么进 PR | 同一个数据 PR（`data/auto-refresh`）：演出有变化才拷贝 `new-concerts.json`，线索有变化才拷贝 `new-leads.json`，`git add` 两个文件；只有线索变了就只带线索，不会带一份只有日期噪声的演出文件。演出有变化时线索文件一起带上（读取日期保持新鲜）。合并、部署、`AUTO_MERGE` 开关和 ADR-0017 完全一样；测试步骤用通过了闸门的新文件跑完整测试 |
| 烟测 | 只有线索闸门放行时才用 `new-leads.json` 构建；扣下的（可能是坏的）文件不能把演出的烟测搞挂 |
| 关闭开关 | 仓库变量 `AUTO_LEADS = false`：不读、不导出、PR 里没有线索，报告里也不再评判线索。`AUTO_MERGE = false` 照旧让所有数据 PR 留给人 |
| 一次性放行 | 手动启动时可选 `accept_leads = true`：只放开“保留 70%”和“新增 60 条”两道计数闸门（比如 オケミン！真的大改版、一次删掉很多已结束的巡演），结构检查照常。定时运行没有输入，永远不会放行 |
| 怎么发现出问题 | `refresh_report.py` 新增线索判断：读取被中止（比如 403）、`leads-sync` 没有输出、线索文件被扣下，都算“需要注意”；最后一步 `--strict` 让任务变红 |

## 为什么线索闸门不会拦演出

线索是第三方个人站点整理的，它出问题（改版、被拦、解析不出）的概率比官方站点高得多；让它拖住官方演出的更新不合适。所以线索的问题只让任务变红，不挡演出。

## 风险和限制

- **线索现在不经人看就上线了。** 防线是：解析时每个页面都要求有乐团块（解析为 0 块就不记为已读、不会让线索“消失”）；上面的 70% / 60 / 结构三道闸门；线索在页面上始终标“未核实”并写明来源。挡不住的是“数量正常但字段读错”（比如日期读错一格）；PR 正文会列出新增 / 变更 / 减少的线索，可以事后抽查。
- オケミン！是个人博客，我们没有找到使用政策（ADR-0007 里 `policy_status` 仍是未知）。每日读取按“间隔 2 秒、先读 robots.txt、遇拒绝即停、只读公开页面”做，稳定后约 10 个请求/天；`AUTO_LEADS=false` 可随时关掉。如果站主表示不希望被读取，应立刻关掉。
- 仓库公开的话，线索的曲目行要去掉（ADR-0007 原话不变）；自动发布让这一点更要紧。
- 数据库里的线索表（`tour_lead`、`lead_page_read`）随云端数据库保存在 Release `cloud-db`。如果数据库是从线上数据还原的（`restore-site` 不还原线索），线索表是空的，下一次读取会重新读全部（线索 id 由内容算出，和已发布的一致），线索文件不会被清空：空表导出远少于已发布的 70% 时闸门会扣下，而不是发布一个空文件。
- **读到一半被中止（比如中途遇到 429）时，已经读到的线索仍可以发布**，只是任务变红。这是有意的：`sync_leads` 只会写入读到的事实；一个年份的线索只有在该年页面完整读完之后才会因为“列表里没有了”而消失，所以半途中止只会让一部分线索暂时没刷新，不会让线索凭空减少；第一次读取（空数据库）半途中止时，导出文件远少于已发布的 70%，由计数闸门扣下。如果改成“中止就整个扣下”，持续性的问题（比如请求上限）会让线索永远冻住。
- 线索的过期（已经结束的巡演）仍由页面在显示时隐藏，文件里的旧线索会一直留着，直到 オケミン！的年度页不再列出它。

## 测试

`tests/test_cloud_publish.py`（`LeadsDecisionTests`）：噪声不算变化、只有线索变化时只带线索、减少的线索会列出、演出变化时线索一起带上、闸门扣下线索但演出照发、新增过多被扣下且手动开关只放开计数闸门（结构检查照常）、文件缺失 / 损坏 / 重复 id / 缺名字被扣下、已发布文件为空时第一次读取放行、演出闸门失败时线索也不发、没有线索参数时输出不变、命令行行为（线索问题不产生退出码 3）。`tests/test_workflows.py`：新步骤的位置和开关、比较步骤的参数、`accept_leads` 只读一次、两个文件各按自己的闸门进入 PR 和测试步骤、烟测只用放行的线索、摘要和红灯检查带 `--publish`。`tests/test_refresh_report.py`：被中止的读取、没有输出、被扣下的文件各算一个问题；`--strict` 的退出码。`tests/test_cli.py`：默认年份按日本时间。`tests/test_leads.py`：后面的年份页还没发布（404）时跳过并继续读文章、不记为已读；读过的年份页突然 404、第一个年份 404、页面没有乐团块仍然中止。
