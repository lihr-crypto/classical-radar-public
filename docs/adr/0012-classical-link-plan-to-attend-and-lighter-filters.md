# ADR-0012 — Apple Music Classical 链接、“预定前往”、日历和搜索的筛选减负

日期：2026-11-17。状态：采纳并实现。**后续**：其中的 Apple Classical 搜索链接已被 ADR-0013 换成直达本人页面（搜索链接在手机 App 里会丢掉搜索词、只打开空的搜索页，且 Apple 的 robots.txt 不允许抓搜索页），下文“Apple Classical 直达”一行以 ADR-0013 为准。起因：用户在上线的 ADR-0011 版本上发来五张手机截图，要求：点曲目、作曲家等能直接跳到 Apple Classical 里的对应页面；像参考图那样，除了 Pickup 再加一个“预定前往”的功能；日历页的乐团筛选太杂；搜索页点了“东京乐团”后，二级筛选和一级筛选的按钮挨在一起。

## 决定

| 问题 | 决定 |
|---|---|
| Apple Classical 直达 | 能做到的是**搜索链接**，不是某一页的直达链接：`https://classical.music.apple.com/jp/search?term=<日文>`（曲目页搜“作曲家 曲名”，人物页搜名字）。核实过：这个网址带搜索词会返回那首作品、作曲家或指挥的结果（用 ブラームス ピアノ協奏曲第2番、ブラームス、藤岡幸夫 试过）。作品页的网址是 `/jp/work/johannes-brahms-1833-pp12`、艺术家页是 `/jp/artist/<数字>`，里面是 Apple 自己的编号，我们的数据里没有，所以不能凭空拼出某一页。iPhone 上的 App 会不会把这个搜索网址当通用链接打开，在这里无法验证，要用户在手机上点一下确认。按钮改名“Apple Music Classical”，替换 ADR-0011 的 Apple Music 搜索；`musicHref` 改名 `classicalHref`，只产生这一个固定网址。我们自己的曲目 / 作曲家 / 人物页保留（它们列出有这首曲子的演出，是之前要的功能），Apple 按钮是页面里的一步跳转 |
| “预定前往” | **按节目的一个开关，和 Pickup 同形**：新表 `user_plan(user_id, concert_id, created_at)`，`PUT / DELETE /me/plans/{id}`、`GET /me/plans`，详情的 `user_plan` 布尔值。是**新表**，所以旧数据库（包括 Release 里的云端数据库）在 `init` 时自动建出，不用迁移（SQLite 改 CHECK 才需要重建表，新表不需要）。线上用的 KV 记录多一张 `plans` 表；**没有 `plans` 的旧记录**在读取时按字段补齐（函数 `read()`、`demo.js` 的 `withDefaults`），不会崩，有测试 |
| 为什么不复用已有的状态 | 每场的状态（想去 / 计划购票 / 已购票 / 已观演…）**不能清除**（接口没有删除入口），做成开关会取消不了；而且新增状态值要重建 SQLite 的 CHECK。新表加开关最小、可撤销 |
| 三层各管什么（别混） | **Pickup** = 想看的节目（按节目）。**预定前往** = 打算去的节目（按节目）。**每场的状态** = 这一场的票和出席进度（想去 / 已购票 / 已观演…，按场次）。“想去”和“预定前往”可以同时开着：前者是挑多场里的哪一天，后者是整场演出打算去。预定前往不创建提醒，也不改任何一场的状态 |
| 界面 | 详情页底部是两个大按钮：“加入 Pickup”（墨色，开了变描边）和“预定前往”（金色描边，开了变实心金色深色字），“官网”退成它们下面的一行。Pickup 页分三块：预定前往、Pickup、已结束（两者里已结束的合并，同一场只出现一次）。没做：日历上标出预定的节目 |
| 日历筛选 | 原来是搜索框、搜索结果、“全部乐团”加芯片、“更多乐团”长列表。现在只剩一行：“全部乐团”加七个乐团（和搜索页同一个函数 `orchFilterChips`）。七个以外的乐团不再能在日历上单独筛，要找它们在搜索框里打名字。`<orch-rules>` 里只剩 `SEVEN_ORDER`、`orchMatch` 和 `onlySeven`（选择里混进七个以外的陈旧 key 会被清掉，筛选不会在没有任何芯片亮着时把所有行藏起来）。删掉：`orchPicker`、`orchOptions`、`orchSearch`、`orchFold`、`calOrchMore`、`calOrchQ` 及对应样式 |
| 搜索页二级行 | “东京乐团”下的乐团行：上方 16px 间距加一条细线，前面一个“乐团”小标签，芯片用小号，和上面一行类别明显分开 |

## 没做的

- **直达某一页**：要有一张“曲目 → Apple Classical 作品页”的对照表。可以抓取 Apple 网站生成，但有认错曲子的风险，还牵涉对 Apple 网站的抓取，没有做。要做的话应当是人工审核的表，只收有把握的名曲。
- **日历标出预定的节目**、**预定前往的提醒**。
- 多场演出里“只预定其中一天”：按场次的状态仍然是那一层。

## 取舍与影响

- 日历少了“按名字搜乐团”和“其他乐团”。理由：它们占掉一屏，而且搜索页的搜索框已经能按乐团名（含中英文名）找。
- 详情页现在有三个相近的东西（Pickup、预定前往、每场的状态），靠上面表格里的分工区分；如果用户觉得重复，最该砍的是每场的“想去”那个芯片，但它保存过的数据仍在，所以这次没动。
- API 多了三条路径（`/me/plans`、`/me/plans/{concert_id}`），登记为合同之外的扩展（`tests/test_api.py` 的 `EXTENSIONS`，`docs/openapi.json` 已重新导出，03_CONTRACTS 加了一行）。

## 验证

- Python：`tests/test_api.py`（开关、重复保存、列表、不影响 Pickup 和每场状态、404、204）、`tests/test_discover.py`（一行一人一节目、其他用户看不到、不产生提醒、旧数据库自动建表）、`openapi` 快照。
- Node：`tests/js/functions.test.mjs`（线上函数：保存、列出、删除，没有 `plans` 的旧记录和只有一张表的很旧记录都能读写）、`tests/js/plans.test.mjs`（`demo.js`：旧的服务器记录和旧的本地存储不崩，保存失败不显示为已保存）、`tests/js/orch.test.mjs`（新的规则块，陈旧 key 被清掉）、`tests/js/browse.test.mjs`（`classicalHref`）。
- 手机宽度截图：详情页（预定前往开 / 关）、Pickup 页（三块）、日历、搜索（东京乐团）、曲目页。
