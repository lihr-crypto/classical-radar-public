# ADR-0008 — 云端自动采集（第一步：手动试跑）与自动确认

日期：2026-11-13。状态：第一步采纳并试跑通过；第二步按下面的决定实现（手动触发先上，定时另开一个小 PR）。起因：用户问“能不能把数据库放云端、自动采集”，并选了“全自动”确认。

> **2026-11-17 更新（ADR-0017）**：下面“不自动确认主办方的节目”和“数据 PR 由人合并”两条已被推翻：现在六个乐团官网和三家主办方（Japan Arts、KAJIMOTO、神奈川艺术协会）都自动确认，每日任务在闸门和测试通过后自己合并数据 PR 并启动部署；开关 `AUTO_MERGE=false` / `AUTO_CONFIRM_PRESENTERS=false` 可以分别关掉。其余（防洪、疑似重复留给人、只确认本次首次看到的候选）不变。

## 决定

| 问题 | 决定 |
|---|---|
| 跑在哪 | GitHub Actions（免费，不依赖这台 Mac）。采集仍然是现有的 `classical-radar sync`，限速、礼貌 |
| 第一步 | `.github/workflows/refresh.yml`，**只能手动触发**：在 GitHub 的服务器上抓一遍并出报告，看日本网站接不接受 GitHub 的服务器。**不提交、不开 PR、不部署、不保存数据库、不用任何密钥**；只留 3 天的小 JSON 和汇总，不上传数据库和原始页面 |
| 为什么不先发布 | 演出、场次、售票阶段的 id 在每个数据库里都是随机生成的（`db.new_id()`），你的收藏、状态、提醒（在 Cloudflare KV 和浏览器里）都是按这些 id 存的。直接用新数据库发布会让这些全部失效。第二步要先解决 id 连续性（用已发布的数据文件给云端数据库打底，或导出时把 id 对回去），再发布 |
| 自动确认 | `classical-radar auto-confirm`（默认只报告，`--apply` 才真确认）：只处理六个乐团官网（NHK 交响乐团、都响、东响、日本爱乐、新日本爱乐、读响；东京爱乐按你的决定暂缓），字段齐全（每场有具体日期、会场、都道府县）、类别是国内乐团的节目。走 `confirm_stored`，原有的检查全部保留 |
| 不自动确认 | 主办方（Japan Arts、KAJIMOTO、神奈川艺术协会）的节目、海外线索、有疑似重复的节目、曾经从来源页面消失过场次的节目——这些仍留给人 |
| 防洪 | 一次运行里符合条件的超过 120 个就一个都不确认（解析器出错或页面改版时，不能一下子上线几十个错的）；试跑只报告，并单独标出“防洪会触发” |
| 输入安全 | 工作流的来源输入只通过环境变量传入，并对照支持列表检查（`scripts/refresh_args.py`），不会拼进命令行 |

## 已知限制

- 云上没有“待确认”界面，所以被留给人的节目要在本地版处理。
- `sync` 即使每个来源都失败也返回成功：汇总会把读到 0 条、HTTP 401/403/429 的来源单独标出。
- 变更事件（改期、列表变化）目前只用“曾经从来源消失”这一种来拦截；第二步发布时只自动确认当次运行首次看到的节目，避免把你特意留在队列里的节目自动确认。
- 第二步见下一节。

## 第一步试跑结果（2026-11-13，run 43342345915）

九个来源全部从 GitHub 的服务器读到（共 526 条，用时约 18.5 分钟，没有 401/403/429，没有被 robots 拒绝）。海外线索 46 次请求、新增 53 条。自动确认试跑：361 场符合、18 场留给人、116 场不在范围内；防洪触发是预期的，因为云端库是空的，所有节目都算新。

## 第二步（2026-11-13 决定）：每天自动跑，经数据 PR 发布

| 问题 | 决定 |
|---|---|
| 云端数据库从哪来 | 这台 Mac 上没有真实数据库。用已发布的 `site-data/concerts.json` 还原（`classical-radar restore-site`，只接受空库）：演出、场次、售票阶段按原 id 写回，线上的收藏、状态、提醒按这些 id 存，所以不会失效。同一场的决定用 `site-data/same_concert.json` 重放。还原不含待确认候选、取消的场次和变更历史，候选由下一次采集重新生成 |
| 数据库放哪 | GitHub Release `cloud-db` 的附件 `radar.db.gz`（仓库私有，不用新密钥），每次运行结束覆盖。Release 不存在时用上面的还原引导；判断“存在与否”靠 `gh release list` 的结果，不靠报错文字，免得网络故障被当成“不存在”而覆盖它 |
| 自动确认 | 带 `--first-seen-after <本次运行开始时间>`：只处理本次首次看到的候选，更早的留给人（计入 `older_candidates`）。防洪在过滤之后计数。**靠还原引导的那一次运行只报告，不确认**：旧候选不在已发布文件里，会都被当成“首次看到” |
| 发布方式 | 先开数据 PR，由人合并（合并到 main 触发现有的部署：测试、构建、部署）。固定分支 `data/auto-refresh`，每次基于最新 main 重建，只会有一个开着的 PR。用两周看数据质量，再考虑直接上线 |
| 什么算有变化 | 忽略 `as_of`、`snapshot_label`、`coverage` 和每场次的 `last_seen_at`（每天都变）；有实质变化，或已发布文件的日期超过 7 天，才开或更新 PR（`scripts/cloud_publish.py`） |
| 安全闸门 | 新文件的演出数少于已发布的 90%、图片比已发布的少（云端取不到图，不能把图洗掉）、一次新增超过 150 场：不上传、不推送，任务失败 |
| 顺序 | 比较和闸门 → 用新数据试构建站点 → 上传数据库 → 推分支和开 PR。闸门没过，什么都不上传 |
| 失败通知 | `sync` 即使所有来源失败也返回 0，所以最后一步自己检查：有来源失败、读到 0 条、或真正执行时防洪触发，任务变红，GitHub 发邮件 |
| 工作流 | `.github/workflows/daily-refresh.yml`。输入 `apply`（默认 false：只报告，什么都不上传不推送）。先只能手动触发；定时在确认过一次 `apply=true` 的运行后用单独的小 PR 加上（见文末“定时上线”）|

已知限制（第二步）：

- 云端库是唯一来源，本地没有库。被留给人的节目（疑似重复、缺字段、曾消失）暂时没有地方处理；之后要做“把云端库拉到本地、确认、再推回”的工具，并防止互相覆盖。
- 靠还原引导的那一次，以及防洪在真正执行时触发的那一次，数据库照常上传。那些候选从第二天起算“更早的候选”，不会再被自动确认，只能由人处理（见上一条，目前没有处理的地方）。这是故意的：宁可少确认，也不让一次出错的运行把一批候选放上线。
- `apply=true` 只在 `main` 上生效；从别的分支手动触发时不会上传数据库，也不会推 `data/auto-refresh`。
- 开 PR 需要仓库设置“Allow GitHub Actions to create and approve pull requests”。2026-11-14 起它已由用户打开。
- 用 `GITHUB_TOKEN` 开的 PR 不会触发 `pull_request` 工作流，所以数据 PR 上没有 CI 检查；工作流自己做了站点试构建，合并后 `deploy.yml` 再跑测试和构建。
- 还原出的售票阶段 `channel` 是占位值 `other`（导出不含它，不影响线上页面）；`poc_performance_id` 在下一次采集碰到该场次时回填。
- 海外线索（leads）不在这个工作流里，仍按原来的方式手动更新。（2026-11-17 起被 [ADR-0018](0018-tour-leads-in-the-daily-run.md) 取代：线索也由每日任务读取并自动上线。）

## 定时上线（2026-11-14）

- 引导运行（run 43549909447，`apply=true`）：九个来源全部成功，`cloud-db` Release 已创建，自动确认只报告（符合条件 54、留给人 14、不在范围内 3）。它开出了第一个数据 PR（#19）。
- 数据 PR 核对：456 场演出一场没少、没多；147 场有变化；售票阶段从 124 条增加到 450 条，**全是新增，没有一条被改或被删**；其余是真实更新（过期场次标为已结束、都响某场标题多了“前売予定枚数終了”、几场曲目和出演者补全）。
- 定时：`schedule: cron '23 19 * * *'`（日本时间每天 04:23；不放在整点，因为 GitHub 常延迟整点的任务）。**定时运行没有 `inputs`**，所以 `APPLY` 改成 `github.event_name == 'schedule' || inputs.apply`，两个上传和开 PR 的步骤改读 `env.APPLY`；否则定时运行会永远只出报告。
- 仍然不会自己发布：数据 PR 要人合并。工作流每天重建 `data/auto-refresh` 并更新同一个 PR，所以隔几天再合并也没问题。
- 引导那一次读到、但没被确认的候选（54 场符合条件）不会被之后的运行自动确认（见第二步已知限制）；需要一次性的人工确认，或给工作流加一个“确认比这个时间更早的候选”的输入。
- 一次性开关 `confirm_older`（手动触发才有，默认关）：打开后自动确认不带 `--first-seen-after`，把引导运行留下的、符合条件的候选一次确认掉；留给人的（缺都道府县或会场）仍然留着。定时运行没有 inputs，所以每天的运行永远不会打开它；防洪（一次超过 120 场就一个都不确认）和发布闸门（一次新增超过 150 场不发布）照常生效。
