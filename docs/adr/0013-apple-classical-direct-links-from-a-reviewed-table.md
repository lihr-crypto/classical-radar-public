# ADR-0013 — Apple Music Classical：直达本人页面（审过的 id 对照表）

日期：2026-11-17。状态：采纳并实现。**后续**：本文“结果”里的曲目覆盖数（104 / 178）只数了有通用 key 的 178 项，漏了 881 项没有 key 的曲目，**不对**；按全部曲目算只有 25%。更正和扩大覆盖见 ADR-0014（对照表现在以“本地 id”为键，也放有名字的曲目和没有 key 的作曲家）。起因：用户在 ADR-0012 上线后用 iPhone 点了“Apple Music Classical”按钮，截图显示 Classical App 确实接管了链接，但只打开了 App 自己的**空搜索页**（搜索词被丢掉，下面是“最近搜索”），不是那位作曲家 / 那首曲子的页面。用户要的是直达对应页面。（**2026-11-20 补充**：被丢掉的是 `?term=`；用户在 iPhone 上试过 `?q=`，搜索词能填进搜索框，所以没有自己页面的曲目现在用 `search?q=` 搜索，见 ADR-0019。下面“不再退回搜索链接”说的是当时的 `term`。）

## 决定

| 问题 | 决定 |
|---|---|
| 按钮去哪 | 作曲家、指挥、演奏家 → `https://classical.music.apple.com/jp/artist/<数字 id>`；曲目 → `https://classical.music.apple.com/jp/work/<slug>`。同一个域名，所以和用户刚验证过会被 App 接管的是同一种链接；这两种具体页面在 App 里是否落在对应页，仍需用户在手机上点一下确认 |
| id 从哪来 | 一张审过的对照表 `src/classical_radar/web/classical-links.js`（`window.CR_CLASSICAL`），由 `scripts/resolve_classical_links.py` 手动生成，不进 CI，也不进每日刷新。三组：`composers`（`composer_key` → 艺术家 id）、`works`（`work_key` → 作品 slug）、`people`（`bfold(名字)` → 艺术家 id，指挥和独奏家共用）。浏览页本来就有这三种 id（`composer_key`、`work_key`、`bfold`），所以前端只是查表 |
| 表里没有 | **不显示按钮**。不再退回搜索链接：搜索链接在 App 里是死路（见起因） |
| 不抓搜索页 | Apple 的 `robots.txt`（classical.music.apple.com 和 music.apple.com）写着 `Disallow: */search?*`、`/query/*`、`/api/*`、`/v1/*`、`*?i=*`。所以 Classical 的**搜索页不能抓**。**更正**：本轮之前我为了验证（ADR-0012 里写“用 ブラームス ピアノ協奏曲第2番、ブラームス、藤岡幸夫 试过”）和这一轮开头，在读 robots.txt 之前一共取过大约 11 次搜索页；这是不该做的，已停止，也在脚本里加了硬拦截（见下） |
| 能请求什么 | 只有两类地址，其它一律抛 `Refused`：Apple 公开、有文档的查询接口 iTunes Search API `https://itunes.apple.com/search?...entity=musicArtist`（不是网页，不在上面那份 robots.txt 的管辖里；用日文名找候选艺术家 id；间隔按文档的每分钟约 20 次以内），和艺术家页 `https://classical.music.apple.com/jp/artist/<数字>`（核对候选是不是这个人，作曲家页还带“有名な作品”15 首的标题、作品号和 slug）。站点地图只有 id 没有名字，没用 |
| 请求的礼貌 | 页面至少隔 2 秒、接口至少隔 3.2 秒；结果缓存在 `evidence/cache/classical`（被 git 忽略），重跑不再请求；有请求总数上限；遇到 403 / 429 立刻停止，且不写表（半张表不能盖掉好表）。UA 同 `network.py`。这一次共约 600 次请求 |

## 怎么认人（严格，认不准就没有按钮）

| 种类 | 规则 |
|---|---|
| 作曲家 | 候选页的日文标题必须是这个 key 的某个已知写法（`works.py` 别名表）才自动通过。只是“包含姓”（ベルク ⊂ シェーンベルク）的**只列出来不通过**，由人逐条看过后写进 `site-data/classical-reviewed.json`（88 条，每条都核对了全名；同姓的人如 ミヒャエル・ハイドン、クララ・シューマン、ガブリエル・プロコフィエフ 都排除了）。页面还要求身份是“作曲者” |
| 曲目 | 只取作曲家页“有名な作品”里的作品；标题交给**我们自己给节目单编 key 的同一个函数** `works.work_key(composer_key, 标题)`，两边得到同一个 key 才算。含 編曲 / 版 / arr. 的不收；同一个 key 对到两部作品的整个丢掉。**只看序号不够**：舒伯特的“第 8 番”在 Apple 是《未完成》（ロ短調），在我们的节目单里是《ザ・グレイト》（ハ長調，D944），两边同一个 key 却是两首曲子，会把“伟大”的页面开成“未完成”。所以生成时还要把表里每一项和**我们自己所有节目单文字**比一遍（`classical_links.clash` / `audit_works`）：调性或作品号和 Apple 的标题不同就整项丢掉；再加一份人工的 `works_skip`：舒伯特 7 / 8 / 9 号（序号两种叫法）、`dukas:symphony-2`（Apple 标题被错编成了 key，杜卡只写过一部交响曲）、`sibelius:symphony-5`（指向的作品号 pp349 跳出了其余西贝柳斯交响曲的 pp25–31，像是另一个版本）。所以只有 Apple 列在前 15 的名曲有按钮（例：贝多芬第 2、4、8 交响曲不在里面，没有按钮） |
| 指挥 / 独奏家 | 候选页的日文标题折叠后必须和我们的名字**完全一样**，页面要有身份（指挥者 / ピアノ…）；两个页面都对得上的算有歧义，不给；Apple 页标题是拉丁字母的对不上，也不给。Apple 有重复的艺术家记录（藤岡幸夫有 265293859 和 382368992），重复的那个在 Classical 站点是 404，所以不会竞争 |

## 结果（2026-11-17 生成）

表里 97 位作曲家、260 部作品、55 位指挥 / 独奏家。按现在的数据看：

| 页面 | 有按钮的比例（按种类） | 按演出次数加权 |
|---|---|---|
| 作曲家 | 84 / 96 | 1051 / 1082 |
| 曲目（有 `work_key` 的 178 个） | 104 / 178 | 433 / 542 |
| 指挥 | 33 / 121 | 219 / 386 |
| 独奏家 | 23 / 311 | 92 / 601 |

人物这一栏**只处理了演出最多的 120 个名字**（其中 55 个通过），其余 322 个没跑（大约还要一个多小时的慢速请求；脚本能增量续跑，已跑的有缓存）。独奏家比例低的原因之一就是这个，另一个是 Apple 上很多日本演奏家的页面标题是拉丁字母。

## 前端

`web/app.js` 的 `<browse-rules>` 里 `classicalHref(dim, id, table)` 换掉了搜索链接构造器：按 `dim` 在表的对应组里查 `id`，用 `hasOwnProperty` 取（`constructor`、`__proto__` 不会当 id），艺术家 id 必须是 `^[1-9]\d{0,11}$`、slug 必须是 `^[a-z0-9-]{3,100}$`，否则没有链接；地址只能是固定前缀加这个 id。表没加载（`window.CR_CLASSICAL` 不存在）也只是没有按钮，不报错。`index.html` 在 `app.js` 之前加载 `classical-links.js`（站点构建时 `site.js` 之前，`build_site.py` 把它复制进去）。

## 没做的

- **未列入前 15 的名曲**（贝多芬第 2、4、8、莫扎特的一些交响曲…）：作品 slug 里有序号（`...-pp24`），但从相邻序号**猜**别的作品是不行的；要补就得逐页取作品页核对标题，没做。（**更正，ADR-0015**：这句说的是作曲家页只读得到 15 部；Apple 公开的作品站点地图加作品页能读到完整列表，ADR-0015 对 18 位作曲家做了。）
- **人物剩下的 322 个名字**、**拉丁字母标题的日本演奏家**：见上。可以另外跑，也可以人工把确认过的 id 写进 `site-data/classical-reviewed.json` 的 `people`。
- **App 里这两类页面是否直接落在对应页**：这里验证不了。用户要在手机上点一下确认；如果 App 仍然只打开首页，要重新想办法（Classical App 没有公开的自定义 URL scheme）。
- **id 会不会变**：表有 `as_of`；刷新就是重跑脚本，由人决定是否提交。

## 验证

- `tests/test_classical_links.py`（不碰网络；脚本自己的 `main()` 没有测试，它的“中途停止不写表、单独跑某一阶段不写表”只由人跑过一遍）：URL 拦截（搜索页、`/query/`、`?i=`、别的域名一律拒绝）、取页的缓存 / 间隔 / 上限 / 403 与 429 停止 / 404 也缓存、真实结构的 Brahms 和藤岡幸夫页面夹具（`tests/fixtures/classical-artist-*.html`）、作曲家的 exact / 只含姓 / 歧义 / 非作曲家 / 复核 id 各一例、曲目的编曲排除与重复 key 丢弃、和节目单文字对照（《ザ・グレイト》对《未完成》丢掉，同一首的不同写法不冲突，作品号不同冲突）、人物的完全一致 / 重复 / 拉丁标题 / 无身份、Python `bfold` 和 `app.js` 里的 `bfold` 对全部演出人名和作曲家名结果一致、已提交的表的形状（key 都在 `works.py` 里、id 是正整数、slug 合规、人物 key 是折叠后的名字、不含网址、不含数据里没有的人）。
- `tests/js/browse.test.mjs`：新的 `classicalHref`（四种页、查不到、表缺失 / 形状不对、`constructor` 等、恶意 id 含路径 / 查询 / 别的域名 / 0 / 前导零，都得 `null`；绝不产生 search）；`tests/js/classical-links.test.mjs`：表里每一项在浏览器规则下都得到固定域名上的地址。
- `tests/test_ui.py`、`tests/test_site.py`：外部地址只允许 `https://classical.music.apple.com/jp/` 一处；站点构建含 `classical-links.js` 且排在 `site.js` 之前。
- 手机宽度截图：作曲家页、有 / 无 key 的曲目页、有 / 无匹配的指挥页（有按钮 / 没有按钮）。
