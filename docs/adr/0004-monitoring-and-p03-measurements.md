# ADR-0004 — 持续监测的语义，以及 P0.3 测量的边界

日期：2026-11-09。状态：采纳（HANDOFF「下一轮任务」第 6、7 项；动手前经评审，评审意见已并入下表）。数字与结论见 [P0.3 报告](../reports/P0_3_ANNOUNCEMENT_AND_JAPANARTS.md)。

## 一、监测（`monitor` / `monitor-report`）

### 要回答的问题

05_ACCEPTANCE 要求记录 `detected_at − official_change_known_at`，并说明“初次 POC 不宣称达到某固定小时 SLA”。真实时效只能靠持续监测积累数据；本轮做的是**可运行、可测试的机制**，没有（也不应该由我）跑长期数据。

### 决定

| 议题 | 决定 | 理由 / 后果 |
|---|---|---|
| 一轮是什么 | `classical-radar monitor DB`：对可监测来源各跑一次现有的 `sync_source`，**只能手动运行**。来源之间、轮次之间不做任何调度；**没有安装定时器，也不提供 cron/launchd 配方** | `monitor` 每次都完整重读来源，等于“定时全站采集”；来源使用政策全部 `unknown`，在政策定下来之前不扩大（HANDOFF 边界） |
| 都响硬排除 | `monitor.MONITOR_EXCLUDED = ("tmso",)`，写在代码里；即使用 `--source tmso` 点名也拒绝并不发请求。`tpo` 本来就在 `DEFERRED` | 都响使用条件限制复用（ADR-0001），不能只靠文档约束 |
| 最小间隔 | 同一来源上一次成功轮次距今不足 `--min-interval-hours`（默认 6）则跳过，`--force` 才忽略 | 防止误循环冲击站点 |
| 不改库表契约 | 报告只读现有表（`ingestion_run`、`change_event`、`concert`…）；唯一新增的是流程表 `page_observation`（见下）和 `counts_json` 里的一个标记 `human_confirmed_import` | 03_CONTRACTS 第 3 行：改契约要先改契约文档、样例、迁移和测试；这里没有改任何契约表 |
| 人工导入不是观测 | 人工 URL 导入确认也会写 `ingestion_run`，但它只读了一页，不是对来源的一次观测。新版本给这类轮次打标记，报告把它排除在“上一轮”之外；人工确认（`verification_status` 事件）也不算官网变化 | 否则上界会被人为压短。**旧版本留下的导入轮没有标记，仍按观测计** |
| 延迟上界 | 每个变化给出 `page_change_to_detection_upper_bound_hours = 发现它的那一轮的结束 − 该来源上一轮成功轮次的开始`。没有更早的成功轮次（含第一次批量入库）时是 **null，不是 0**，并写明原因 | 旧值最晚在上一轮开始后才被读到，新值最迟在本轮结束前被读到，官网必然在这期间改过，所以我们的延迟不会超过它。名字里写明“页面变化到发现”，免得被读成“距官方公布多久” |
| 事件与来源的对应 | 通过变化事件的实体（`concert` / `performance` / `ticket_phase`，后两者经 `concert`）找到来源；通过 `detected_at` = 该轮 `started_at` 找到对应的那一轮，不靠“最近一轮”猜 | 评审要求 |
| 官网变化时间 `official_change_known_at` | **部分可知**：P0.3 发现 Japan Arts、东京交响乐团、神奈川艺术协会、KAJIMOTO、新日本爱乐 5 个来源的详情页带“页面最后修改时间”（JSON-LD `dateModified`、`article:modified_time`、`og:updated_time`）。每次读详情页，`pageobs` 把它（连同规范化后的网址）记进 `page_observation`。报告只在三道保护都过了才把它当作 `official_change_known_at`：(1) 之前**已经有过一次带修改时间的观测**可比（第一次观测，或升级后的第一轮，没有基线就不用，否则会给每个变化挂上很老的保存时间）；(2) 这个时间比上一次观测**往后移动了**；(3) 它**不早于上一轮的开始**（否则是缓存或我们已经看过的编辑）。通过后给出 `detected_minus_official_change_hours`（与契约字面一致）。只有日期的戳不给点值，给 `..._range_hours`（按日本时间的一整天算的区间），也不并入中位数。其余来源、列表页层面的变化、没通过保护的变化都是 null 并写明原因 | 页面修改时间是内容管理系统的保存时间：任何编辑都会改它，不等于实质变化，也不是主办方公布变更的时间。这是现有唯一的抓手，所以用，但不夸大 |
| 之前的错误说法 | 本 ADR 的前一稿和 `monitor.py` 的第一版说“没有来源暴露官网变更时间”。写 P0.3 报告时发现这不对，已改正 | 记录下来，避免旧结论被引用 |
| 解析器版本 | 变化事件也可能来自两轮之间的**解析器改动**，而不是官网；运行记录里没有代码版本。报告的 notice 里写明了这一点 | 没有就老实写没有 |

### 没做

- **没有跑过任何真实的监测轮次**：长期数据（轮次间隔、变化数量、延迟分布）只能在你本机手动跑 `monitor` 积累；报告在没有数据时返回空而不是编造。
- 新增公演的发现延迟：没有官网的“发布”时间能参照（P0.3：只有 3 个来源有页面发布时间，且只有页面级），所以只报告每轮新增数量。
- 提醒投递、通知与监测没有联动。

## 二、P0.3 测量的边界

| 议题 | 决定 |
|---|---|
| 真实读取的范围 | 一次性、有上限、礼貌：8 个 source_id（`japanarts kajimoto yomikyo nhkso tso njp jpo kanagawa_geikyo`），**不含** `tmso`、`tpo`；先读 robots.txt，读不到按禁止；每个网址一次运行只取一次；每站 ≥2 秒；401/403/429 即停；单次运行硬上限 120 个请求（代码强制，超限中止）。实际三次真实运行共 144 个请求，每次都未超限 |
| 提交什么 | 只提交 ≤200 字的片段与判定；整页只保存在被忽略的 `evidence/raw/`（不提交完整网页）。`scripts/check_p03_evidence.py` 检查大小、片段长度、抽样规则、计数、与报告数字一致，并在 CI 里运行 |
| “首次公布日期”的口径 | `published` 只收：JSON-LD `datePublished`、`article:published_time` 等机器戳，或“公開日/掲載日/発表日/投稿日/配信日”标签，并且日期**严格早于**该页最早演出日；机器戳还要求同一来源各页取值**不全相同**（防模板戳）。`更新日`、`dateModified` 等只算 `update_only`；无标签日期（如 NHK 新闻页的 `class="date"`、神奈川页里其实是演出日的 `span.published`）只算 `ambiguous` |
| 分母 | n = 实际取到的页数，N = 列表给出的页数；抽样规则（排序后均匀取 8 个）和抽到的网址写进证据。`fetch_failed` 与 `none` 分开计；`none` 只读作“抽样的详情页上没有日期”，**不读作**“官网没有公布” |
| 页面发布时间 ≠ 首次公布 | 3 个来源的页面发布时间，**只有在它确实是页面对外可见的时间时**才是首次公布时间的上界；这个时间可被编辑或回填，从外部无法核对，也没有证据说明它等于主办方首次对外公布的时间。本轮**没有**改解析器，也**没有**写 `official_announcement_date`；要不要用、用什么标签，留给你 |
| Japan Arts 的“核对” | 称为“程序比对 + 我的复读”，**不称**“已核实/人工核对”：解析结果与页面可见文字、与站点自己的列表卡片互相一致（42/42）。列表卡片检查能发现“丢了/改了本页场次”，发现不了“多出一场”（ERRATA E1 的形态）；后者只有跨页提示能部分看到（4 条，全是系列页与分场页的正常重叠）。它与解析器读的是同一页，不是独立真值；售票时刻和类别判断仍列为未解决（见报告） |
| 请求计数与重复读取 | 前三次真实运行按“每次调用 `Reader.get` 记一次”统计，重定向跳转没有单独计入；现在的探测脚本按实际发出的请求计数（含重定向），上限也按它执行。“每个网址只取一次”只在单次运行内成立：第二、三次运行重读了缓存里还原不出来的来源（读卖页面没有 canonical，神奈川列表页对不上）和检测规则漏判的来源，共 36 个请求 |
| 开售时刻覆盖 | 离线重放缓存页面（0 个请求）：用页面可见文字里的开售行（Japan Arts 只看自己的开售区块；年份写了就用，没写由括号里的星期确定）与现有解析器逐页比对；n/N 就是 P0.3 公布日期探测的抽样。只是测量，`salecoverage.py` 没有接进入库；KAJIMOTO 与 NHK 的“未来开售”数字来自 P0.2 证据的完整名单。报告：[P0_3_SALE_TIME_COVERAGE.md](../reports/P0_3_SALE_TIME_COVERAGE.md) |
| 证据重放 | `--replay-raw` 用缓存页面（按页面里的 canonical/og:url 对应网址）离线重算，不发请求；`--merge-into` 只替换被重新探测的来源，并把每次运行记进 `runs`。检测规则第一版漏了无标签日期，所以三个来源补读了一次（24 + 12 个请求） |
