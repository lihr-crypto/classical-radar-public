# ADR-0014 — 曲目的“写法折叠”，和 Apple Classical 按钮的覆盖面

日期：2026-11-17。状态：采纳并实现。起因：用户在 ADR-0013 上线后发来一张手机截图（曲目页《亡き王女のためのパヴァーヌ》，3 场演出，没有 Apple 按钮），说：有些曲目没有合并到同一栏、而是分开统计，也跳不到 Apple Classical；还有很多指挥、作曲家也跳不了，为什么？

## 查出来的

| 现象 | 原因 | 数字 |
|---|---|---|
| 同一首曲子分成几项 | 没有 `work_key` 的曲目按“作曲家 + 折叠后的曲名”分组，而折叠（`bfold`）不管引号、括号、标记和“op. / 作品”的写法。`組曲《展覧会の絵》` 和 `組曲「展覧会の絵」`、`幻想交響曲 op.14` 和 `作品14`、`ボレロ` 和 `「ボレロ」` 和 `ボレロ*` 都是两项。ADR-0010 把它列为“已知缺口”，当时的理由是“只按写法分、不按相似度合并” | 真实数据 37 组 |
| 《亡き王女のためのパヴァーヌ》没有按钮 | 这页其实是**一项**（3 场演出写法相同），没有按钮是因为它没有 `work_key`（不是“第N番”这种通用写法），而 ADR-0013 的对照表只按 `work_key` 放曲目 | 折叠前曲目 1059 项里 881 项没有 key（178 项有） |
| 很多作曲家没有按钮 | 对照表只放了 `composer_key`（别名表里的 96 位）；没有 key 的 219 个作曲家写法（ブルッフ、ペルト、レハール、J.シュトラウスII世……）从来没查过 | 310 场次 |
| 很多指挥 / 独奏家没有按钮 | ADR-0013 只查了演出最多的 120 个名字；查过的里面，29 位在 Apple Music 有主页但在 Classical 站点上没有页面（打开是 404），30 位 Apple 上没有古典艺术家，4 位是拼写差一点 | 另有 322 个名字没查 |

**更正（ADR-0013 / PR #28 里我报的曲目覆盖数不对）**：我当时写“曲目 104/178、433/542”，分母只数了 178 个有 `work_key` 的曲目，漏掉了 881 个没有 key 的曲目。按所有曲目算，当时只有 104 / 1059 项有按钮，占演出次数的 25%。

## 决定

| 问题 | 决定 |
|---|---|
| 写法折叠 | 新增两个纯函数（`web/app.js` 的 `<browse-rules>`）：`workFold`（曲名）和 `nameFold`（人名、作曲家名）。只处理**写法，不处理内容**：`《》「」『』〈〉“”‘’"'()（）[]【】` 这些引号 / 括号符号去掉；`* ★ ☆ ◆ ◇ ♥ ※ ● ○ ■ □ ▲ △ ♪` 这些抄页面时带进来的标记去掉；“op. / Op. / 作品”后面跟数字时统一写成 `op`（这是把“作品”这个词改写成 `op`，规则固定，不看相似度）。**不动**的：作品号和目录号、调性、第N番、乐章、括号里的文字（所以 `(M. ラヴェルによる管弦楽編)`、`(1919年版)`、`より…` 都还是不同的曲子）、“他”。括号夹在两个数字之间时留一个分隔符，所以 `op.10(12)` 和 `op.101(2)` 不会变成同一个数字。人名只去掉标记（真实数据里 4 个名字带标记，例如 `カミラ・ニールンド◇`）；同名不同人、`北村陽` 和 `北村陽子` 仍然是两项 |
| 这算不算“按相似度合并” | 不算。只是把固定的几个字符按固定的方式写成一样，和 `bfold` 折叠全角半角、点、连字符是同一类事；不比较编辑距离，不猜“像不像”。03_CONTRACTS 3.2 禁止的是把**同名不同人**自动合并，这里没有碰 |
| 旧地址 | 以前的 `#browse/work/~作曲家|<旧折叠>` 地址，页面会把 `|` 后面的曲名再折叠一次（`canonWork`），落到新 id；`workFold` 是幂等的（折两次不变），有测试。`work_key` 的 id 和人物 id 原样通过 |
| 对照表的键 | 改用**本地 id**：一行节目单自己就带的 id（`work_key`，没有就是 `~(composer_key 或折叠名)|workFold(曲名)`；作曲家是 `composer_key` 或折叠名；人是 `nameFold(名字)`）。以前用的是页面当前加载的演出列表算出来的 id，而 12 / 24 个月视图、每日刷新都会让它变，表里的键会悄悄失效。页面（`classicalIds`）把“自己的 id、地址里写的 id、被页面并进来的每一行的本地 id”都拿去查表，**得到两个不同的答案就不显示按钮**（不会选一个猜）；一个都查不到也是没有按钮 |
| id 从哪来 | 脚本 `scripts/browse_entities.mjs` 用 `app.js` 自己的规则对 `site-data/concerts.json` 算出本地 id，再交给 `scripts/resolve_classical_links.py`，所以表的键不会和页面的 id 漂移 |
| 有名字的曲目 | 对照表增加“有名字的曲目”：作曲家页“有名な作品”里 Apple 的标题，去掉标记、括号、作品号 / 目录号、调性后，必须和我们的标题完全一样，在 Apple 的 15 部里唯一，不是纯体裁词，和我们的文字不冲突。程序**只提出建议**，我把每一条（我们的标题、Apple 的标题和作品号、slug）逐条读过，才写进 `site-data/classical-reviewed.json` 的 `works`（61 条）；脚本每次还会检查它的 slug 仍在该作曲家的作品列表里 |
| 太泛的标题不自动配 | “纯体裁 / 乐器词”的标题（ピアノ協奏曲、夜想曲、前奏曲、セレナード、ロマンス、序曲、舞曲、ソナタ、ヴァイオリン・ソナタ第2番、レクイエム、エア、ロンド……）不提建议：它在 Apple 前 15 里只出现一次，不等于作曲家只写过一首。同理，**我们这边**的文字带 編曲 / 版 / arr. 或 より / から / 抜粋 / 楽章 / 第N曲 / 他 的不提建议（那不是整部作品）。冲突检查也加了目录号：同一种目录（K / BWV / D / Hob / RV / Sz / FWV / WAB / op …）号码不同就丢掉，不只是调性和作品号 |
| 没有 key 的作曲家 | 按名字查：Apple 页面标题必须和我们的名字完全一样才自动通过（5 位）；只是“包含姓”的（ブルッフ ⊂ マックス・ブルッフ）逐条读过、对出生年，才写进复核文件（24 位，同姓的人如 ルーペルト・フーバー、ベルトルト・フンメル 排除；**リンドベルイ**〔节目单是 ヴィオラ協奏曲，是 Magnus Lindberg，Apple 候选是 Christian Lindberg〕和 **ロウ**〔Frederick Loewe，Apple 候选是另一个 Rob Lowe〕不收）。只处理演出 2 场及以上的 53 个；只有 1 场的 166 个没有按钮。`J.シュトラウスII世`（12 场，别名表漏了这个写法，ADR-0010 的缺口）手工对到 Johann Strauss II 的页面 |
| 指挥 / 独奏家 | 把剩下的 322 个名字也查了（约 520 次慢速请求，规则同 ADR-0013）；查询用的名字去掉标记，Apple 标题前面的“指揮:”这类角色前缀去掉再比。两位拼写差一点、身份确定的（ニコライ・シュコフ = Nikolay Schukoff，トマシュ・コニエチュニー = Tomasz Konieczny）手工写进复核文件。Apple Music 里有、Classical 站点上没有页面的人（29 位）仍然没有按钮：music.apple.com 的链接会打开 Music App，不是 Classical，这个没有替用户决定 |

## 结果（2026-11-17 生成）

表里 127 位作曲家（88 + 24 手工复核的写法 + 1 个手工对应 + 14 自动）、321 部作品（260 通用 key + 61 有名字的）、158 位指挥 / 独奏家。

| 页面 | 有按钮的项 | 按演出次数加权 | PR #28 时 |
|---|---|---|---|
| 作曲家 | 114 / 315 | 82% | 75% |
| 曲目（折叠后按本地 id 算共 1031 项） | 165 / 1031 | 33% | 25% |
| 指挥 | 62 / 121 | 68% | 57% |
| 独奏家 | 97 / 310 | 32% | 15% |

曲目页的合并：真实数据里曲目项从 1059 降到 1030（页面索引；按本地 id 数是 1031，差 1 是解析时有一个无 key 的写法被并进了有 key 的曲目）；解析时 `makeResolver` 的“一个写法对到两个 key”的集合在折叠前后都是空的，原有的并入一个都没丢。

## 曲目为什么多数还是没有按钮

| 原因 | 项数 | 演出次数 |
|---|---|---|
| 有名字的曲目，但不在 Apple 列的前 15 部里（或标题对不上，例如我们写“交響詩《フィンランディア》”，Apple 写“フィンランディア”） | 约 290 | 约 430 |
| 作曲家没有 Apple Classical 页面（或是只有 1 场的作曲家，没查） | 约 260 | 约 295 |
| 编曲 / 节选（より、楽章、編曲…） | 约 135 | 约 180 |
| 纯体裁的标题（ピアノ協奏曲 ト短調 op.26、前奏曲 ハ長調 BWV531…） | 约 100 | 约 135 |
| 有通用 key 但不在前 15 部里（贝多芬第 2 号交响曲…） | 约 75 | 约 110 |

要再提高，得逐页取 Apple 的作品页核对标题（没做）；不会从相邻的 slug 编号去猜。

**更正（ADR-0015）**：“逐页取作品页”后来做了一部分：作品站点地图（robots.txt 列出）给出地址，一页读一个标题；18 位作曲家的完整列表已读，曲目页按演出次数的覆盖从 33% 到 37%。仍然不从 slug 编号去猜。

## 没做的 / 已知缺口

- `J.シュトラウスI世` 等写法没有合并进别名表对应的 key（要改 `works.py` 的别名表并重新给已发布的数据编 key）；`J.シュトラウスII世` 现在有 Apple 按钮，但仍是和 `J.シュトラウス2世` 分开的两项。
- “前 15 部以外”的曲目、Apple 只在 Music 里有的艺术家、拉丁字母标题的日本演奏家：没有按钮。
- 不带数字的单部作品，如 `ピアノ協奏曲 イ短調`（舒曼、格里格各只有一首）因为是“纯体裁词”，不会自动配；要加，手工写进复核文件。
- 12 个月视图里，如果表里认识的写法只出现在 13～24 个月之后的演出里，这一页可能暂时没有按钮（宁可没有，不会指向别处）。
- 脚本里 `main()` 本身没有自动化测试；“中途停止不写表、单独跑某一阶段不写表”只由人跑过。

## 验证

- `tests/js/browse.test.mjs`：`workFold` / `nameFold` 的合并（引号、括号、标记、op / 作品）和不合并（作品号、调性、目录号、第N番、编曲注记、“他”、括号夹数字）固定用例；幂等；旧地址落到新 id；索引里变体合成一项且页面列出全部演出；`classicalIds` 的 id 来源、两个 id 答案不同时没有按钮、一个也没有时回到页面 id 和地址 id；真实数据上索引变少、没有丢掉的并入、每个条目的数字等于它页面列出的场数。
- `tests/test_classical_links.py`：`name_fold` 与 `app.js` 的 `nameFold` 对全部人名一致；每条节目单标题折叠后是不动点；`core_title`、`is_generic`（审稿人点名的 ピアノ協奏曲 / 夜想曲 / 前奏曲 / セレナード / ロマンス / 序曲 / 舞曲 / 交響曲 / ソナタ / 四重奏曲 都算纯体裁）、`excluded_text`、目录号冲突；`propose_works`（有名字的通过；纯体裁、编曲 / 节选、Apple 两部同标题、冲突、通用 key 都不提）；没有 key 的作曲家和人物的名字解析；节点脚本 `browse_entities.mjs` 的输出；已提交的表：键的形状、作曲家的 key 和折叠名两个命名空间不相交、有名字的曲目 id 里的标题已折叠且作曲家在表里（不要求数据里此刻还有这些演出，演出每天会过期）。
