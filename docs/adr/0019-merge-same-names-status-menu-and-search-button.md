# ADR-0019 — 同一个作曲家 / 曲目合并，去掉“其他状态”菜单，没有自己页面的曲目改去 Apple 搜索页

日期：2026-11-19。状态：采纳并实现。起因：用户看着手机上的线上页面，发了两张截图（详情页的日程卡带着“其他状态”下拉；一首曲目页上虚线的“Apple Music Classical｜作曲家页”按钮），说了三件事：**“那些其实是同一个作曲家或者同一个曲目的能合并的都合并”**、**“其他状态删掉”**、**“没有按钮的曲目能不能不要跳转到对应作曲家页面，而是跳转到搜索界面，搜索框里填上对应的曲目名”**。

## 决定

| 问题 | 决定 |
|---|---|
| “其他状态” | 日程卡上只剩 想去 / 已购票 / 已观演 三个按钮，下拉菜单整个去掉（`stateRow`、`.status select`）。接口、数据库、KV 照旧接受 计划购票 / 已申请 / 已中签 / 放弃 四个值：以前存过的还在，Pickup 页还是原样显示；详情页上它们不再有入口（也一直没有清除的入口，点三个按钮之一会覆盖它）。**取代** ADR-0011 里“每场保留 … 其他状态”那一句 |
| 没有自己 Apple 页面的曲目 | 虚线按钮改成 `Apple Music Classical｜搜索`，指向 `https://classical.music.apple.com/jp/search?q=<作曲家 曲名>`，点开 Classical App 就是搜索页，作曲家和曲名已经填在搜索框里。**取代** ADR-0016（作曲家页按钮）。作曲家页那个回退整个去掉，所以连“作曲家也没有 Apple 页面”的曲目现在也有按钮（只要有曲名）。**2026-11-19 的第一版是 `?term=` 加“点的时候复制曲名”，2026-11-20 改成 `?q=`，见下** |
| 参数为什么是 `q`（2026-11-20 更新） | ADR-0013 记录过：用户在 iPhone 上点 `?term=` 的搜索链接，Classical App 接管了链接，但**把 `?term=` 丢掉，只打开空的搜索页**。2026-11-19 我先做了“点的时候把曲名复制到剪贴板，到搜索框粘贴”（网页没法替人在别的 App 里粘贴）。用户随后给了一个参考 App（演奏会びより：点 Apple Music 按钮就自动搜索），我做了一页测试页（六种链接写法：`term` `q` `query` `searchTerm` `text`，以及普通 Apple Music 的 `search?term=`），用户在 iPhone 上逐个点，**`?q=` 能把词填进搜索框**。于是改成 `?q=`，**复制到剪贴板那一步整个去掉**（`copyTitle`）。用户只报告了 `?q=` 可以，其余几种写法的结果没有记录 |
| 这和 ADR-0013 / robots.txt 冲突吗 | 不冲突。ADR-0013 不放搜索链接，理由是“链接到了也是死路”（那时用的是 `term`）；`q` 能填词，不再是死路。robots.txt 不让**爬虫**取搜索页：我们的代码从不请求这个地址，只是用户点的时候由 App / 浏览器打开。`tests/test_ui.py` 仍然保证：自己页面的规则（`classicalHref`）造不出 `/search`，搜索地址只有 `classicalSearchHref` 一处（固定前缀 + `search?q=` + 编码后的一段文字，最长 100 个字，不含换行和控制字符），并且代码里不再出现 `search?term`，曲目页这一段（`browseEntity`）里不再有剪贴板调用，搜索的文字是“作曲家 曲名”（`classicalSearchHref([ent.sub, ent.label]…)` 一行也被固定住） |
| 搜什么 | **作曲家 + 空格 + 曲目页标题那一行**（索引里写得最多的写法）。用户测试页里用的就是“作曲家 曲名”，参考 App 也是这样；只搜曲名的话“交響曲第5番”会搜出所有作曲家的 |
| 合并 | 在浏览器里做（`app.js` 的 `<browse-rules>`），见下表。**不改任何已存 id、不改接口、不改 `works.py`** |

## 合并怎么做

核心约束：**苹果链接表（`web/classical-links.js`）用“本地 id”查**（`localComposerId` / `localWorkId`：一行节目自己就能算出的 id，ADR-0014），合并只改**页面 id**，而 `classicalIds` 本来就把并进这一页的每一行的本地 id 都交给链接表查，所以合并不会丢链接；本地 id 一个字都没改。（也因此不动 `works.py`：给 `works.py` 加别名会让已有行重新有 key，它们的本地 id 变了，链接表里按旧 id 存的条目就丢了；PR #40 也在重生成这张表。）

| 规则 | 做什么 | 不做什么 |
|---|---|---|
| 作曲家：编曲者备注 | 结尾括号里有「編」「編曲」「アレンジ」「arr」「版」「補筆」「校訂」「訳」的去掉（`J.ブラームス (阪田知樹 編曲)` → `J.ブラームス`）。括号被截断的（`ラヴェル(志村和音`）只在剩下的是已知名字时才去 | `世界三大ヴァイオリンメドレー(ベートーヴェン` 这种被括号截断的曲名不当作作曲家；`coba(小林沙羅作詞)` 作词不是编曲，不动 |
| 作曲家：人工审核别名表 `COMPOSER_ALIAS` | 带缩写的写法（P.チャイコフスキー、W.A.モーツァルト、F.リスト、G.ヴェルディ…）、小约翰·施特劳斯的各种写法（J.シュトラウスII世 / ヨハン・シュトラウスII / シュトラウスII / シュトラウスII世 → `j-strauss-ii`，I世同理）、`バッハ=ブゾーニ` 这类“原作曲家=编曲者”署名 → `bach`、エンニオ・モリコーネ、シャルル=マリー・ヴィドール、グノー=リスト編。每一条都对着真实数据看过。`tests/test_ui.py` 检查每个 key 目标都是 `works.py` 里真有的 key | **光秃秃的姓不列**：`シュトラウス`、`アダムズ`、`ロウ`（≠ Rob Lowe）、`ノルドグレン`（没核实是不是同一位）、`ファニー・メンデルスゾーン=ヘンゼル`（≠ メンデルスゾーン）都保持原样 |
| 曲目：长音符号 | 页面 id 的折叠再去掉 ー（ラプソディー / ラプソディ，サクソフォーン / サクソフォン） | 本地 id 的折叠（链接表用的）不变 |
| 曲目：作品号 / 目录号 / 调号 / 年份有无 | 同一作曲家、**去掉调号、作品号、目录号（K. BWV D S RV WAB Hob B R…）、括号里的年份、类别词（歌劇 交響詩 バレエ…）之后标题相同**的各种写法并成一项，页面 id 是去掉这些之后的标题。例：大学祝典序曲 `op80 / 无 / ハ短調 op80`，英雄の生涯，威風堂々第1番，さすらい人 `D760 / D760 Op.15`，ボレロ / バレエ音楽『ボレロ』，ローマの噴水 / 交響詩「ローマの噴水」 | 要同时满足：①去掉之后的标题有至少两个“不是体裁词、数字、‘第 番 の と’”的字（`序曲` `ロンド` `ソナタ第19番` `夜想曲 no.2` `舟歌` `ピアノ協奏曲第1番` 都不算够具体）；②这一族里**作品号最多一种、目录号最多一种、调号最多一种、年份最多一种**，否则整族一首也不并（Mozart ロンド K.485 / K.494，Rachmaninoff 12の歌曲 Op.14 / Op.21，Dvořák スラブ舞曲 op.46 / op.72，Bach 前奏曲 BWV531 / BWV548，Tchaikovsky くるみ割り人形 op.71 / op.71a，Sibelius 5番 1915 / 1919）。“より / から”（节选）写在标题里，所以节选永远是另一首 |
| 曲目：译名行 | 日文行**紧跟着**同一作曲家的英文行，并且作品号相同、或目录号相同、或曲号相同且体裁对得上（Symphony↔交響曲 …）→ 英文行并进日文行那一首，不再单独成项；两行对不上的（Ruslan and Lyudmila Overture、藤倉大 Radiance for orchestra）各自成项。同一个英文写法只要有一处不满足条件，就处处不并（一个地址不能是两页） | 不靠“同一作曲家的下一行”这一点就并 |
| 曲目：演奏者署名 | 结尾括号里的名字**全部**是这场演出自己的指挥 / 独奏者（`(ピアノ:桑原志織)`、`(藤田真央)`）→ 当作署名去掉；冒号前的“ピアノ：”“コンサートマスター：”这类角色词不算名字；名字至少两个字 | 括号里有不是这场艺人的字（“(ピアノ・ソロ)”“(1919年版)”“(全5曲)”）就不动。注意：节目里的室内乐署名多数记成角色 `other`，卡片上没有这些人，所以这条规则在真实数据里只命中少数几处 |

页面 id 的变化：没有 key 的曲目 id 现在是 `~作曲家 id|去掉作品号等之后的标题`（以前是整个折叠标题）。旧地址（书签、主屏幕、分享出去的）靠 `canon` 找得到新页：每一行的每种写法（原文、去掉署名的、去掉作品号的）都登记到它落在的页面，一族后来因为多了一个作品号而拆开时，旧的“去掉作品号”地址落到该族里最小的 id（总有页面，不会空）。24 个月和 12 个月的数据里 id 可能不同，这一点 ADR-0010 以来就是这样。

## 真实数据上的结果（`site-data/concerts.json`，539 场，不分窗口）

| 曲目条目 | 1055（749 项只有 1 场） | 1007（698 项只有 1 场），并了 36 组，全部是同一首 |
| 有自己 Apple 页面的作曲家（按演出次数） | 1145 / 1413 | 1167 / 1412 |
| 有自己 Apple 页面的曲目（按演出次数） | 711 / 1729 | 728 / 1714 |
| 链接表里 id 互相矛盾的页面（会变成没按钮） | 0 | 0 |

并起来的每一组我都读过一遍（脚本输出放在 PR 说明里）。有一处是取舍：Bach 的 シャコンヌ（原曲、ブゾーニ编、ブラームス编）因为署名并成了 Bach，标题一样所以并成一项；以前同一作曲家下标题相同、乐器不同的行本来就是并的，这里保持一致。**改编版只在标题里明写了不同的名字时才分开**（“…(ラヴェルによる管弦楽編)”“…(ピアノ独奏版)”仍是另一项）。

## 没做 / 没合并的

- **`works.py` 的别名没动**：新数据里写成 `P.チャイコフスキー` 的行仍然没有 key，由页面的别名表接住（别名表是长期的，不是过渡）。要动 `works.py`，得连同链接表一起重生成（与 PR #40 协调）。
- **译名行的入库**：想过让 `works.py` 的 `_LATIN` 认引号、入库时就跳过这些英文行，改回来了：会丢掉“紧跟日文行的、其实是另一首的英文标题”，而页面里的证据规则不丢数据。
- **词序不同**（フィンガルの洞窟序曲 / 序曲「フィンガルの洞窟」）、**标题太泛的**（ソナタ、ロンド、夜想曲、舟歌…）、**日文标题没有英文标题能对上的**、**署名里是没记成指挥 / 独奏者的人**：仍然分开。
- **曲名里带“より / から”的节选**、**不同编制的改编版**：另一项。

## 验证

- `tests/js/browse.test.mjs`：每条规则的固定用例（含上表“不做什么”的全部反例）、旧地址和详情页链接都落在列出这场演出的页上（真实数据文件上也查）、合并页的链接表 id、一族拆开后旧地址还能打开页面、链接表里两个 id 指向两个页面时不出按钮。`tests/test_ui.py`：别名 key 都是真 key；搜索地址只有一处；`stateRow` 里没有菜单。
- 真实数据上逐组审计：作曲家 19 组、曲目 36 组，链接表矛盾 0。
- 手机宽度截图：详情页日程卡（没有菜单）、没有自己页面的曲目页（新按钮）、合并后的作曲家页 / 索引。
