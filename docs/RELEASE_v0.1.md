# Classical Radar v0.1（初版，个人本地使用）

2026-11-04。这是一个**能用的最小版本**：从官方来源取得日本古典音乐公演 → 人工确认 → 在网页里发现、看详情、Pickup、看日历、记录个人购票状态。不是公开服务，没有部署，没有任何外发。

## 快速开始

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.lock && pip install --no-deps -e .

export CLASSICAL_RADAR_TOKEN="$(python3 -c 'import secrets;print(secrets.token_urlsafe(24))')"   # 至少 16 字符；没有它服务拒绝启动
classical-radar sync data/radar.db            # 手动、限速（每站 2 秒/请求）。全量约 6–8 分钟；可用 --source japanarts 只取一个
classical-radar serve data/radar.db           # http://127.0.0.1:8000/ ，在页面里输入上面的令牌
```

在网页“待确认”里核对候选（每条有来源链接和页面原文），勾选后“确认选中”，它们才会出现在“发现”和“日历”。

## 能做什么

| 页面 | 内容 |
|---|---|
| 发现 | 官方确认的未来 12/24 个月公演；类型筛选；**作曲家 / 作品 / 指挥 / 演奏者 / 场馆结构化筛选**（同维度“或”、跨维度“且”，候选值来自已收录数据）；首都圈优先或全国按公布时间；发现页按类型分成书架：主办方公演、钢琴独奏会、在京七团（乐团可逐个筛选）；同节目多场一张卡（日期范围加场数）；时刻未公布时写“时间未公布”，不猜；搜索页有文字搜索、类别和上面的结构化筛选；在详情页点“加入 Pickup”（不开启任何提醒） |
| 详情 | 出演者（含角色）、曲目、全部场次、场馆、售票阶段（只显示官方公布或有证据关联的时刻）、场次级个人状态（想去…已观演）、官方页面链接 |
| 日历 | 月历，“演出日 / 开票日”两种视图，点日期看当天列表；只有日期的开售按全天，不补具体时刻；只有日期的演出时刻画成 `––:––` |
| 我的 | Pickup 列表及各场次状态 |
| 待确认 | 候选审核（批量确认、改类别、补都道府县）；粘贴官方 URL 暂存→核对→确认 |
| 来源 | 每源已存数量、最近一次运行结果，不给覆盖率百分比 |

## 可在线试用的演示页

`scripts/build_demo.py DB OUT.html` 把数据库里已确认的节目打包成一个只读的单文件网页（界面代码与本地版相同，`demo.js` 在浏览器里代替后端）。收藏、我的状态和提醒只存在浏览器里；没有待确认队列和 URL 导入。`scripts/check_demo_parity.py DB DATA.json` 验证演示后端与 Python 实现返回相同的节目与顺序（筛选、分页、分面、日历共 17 项）。生成的网页含抓取的官方页面事实，来源许可未明，**不要入库或公开**（`data/` 已忽略）。

## 照片

`classical-radar images data/radar.db` 为已确认节目的指挥、独奏者和乐团查找维基共享资源上自由许可的照片（严格同名匹配，带署名与许可），缓存在 `data/media/`，网页与 `scripts/build_demo.py` 会自动使用。官方海报与主办方照片受著作权与使用条件限制，不抓取。没有照片时封面是按类型着色的色块（主办方公演群青、钢琴独奏石墨、乐团常盘绿），上面的大字只取自标题和出演名单里已有的内容：第 N 回、《》「」里的曲名、出演者名或主办方代码，规则见 [UI_DIRECTION](UI_DIRECTION.md)，不编造信息；有照片时用照片做封面。云端环境访问维基媒体被拒，所以这一步需要在你自己的电脑上运行。

## 已知限制（请在使用前了解）

1. **数据只是候选，质量取决于你的确认。** 解析器已发现并修复过真实错误（见 `evidence/p02/ERRATA.md`）；Japan Arts 仅 7 页做过逐块人工对照。售票时刻：Japan Arts、东响、神奈川（含套票）现在也会读（2026-11-09 补解析，见 [ADR-0005](adr/0005-sale-time-parsing.md)）；多场演出的页面读出了也不挂到场次；日本爱乐页面只有“发售中”之类的说明；读卖没有年份和时刻。
2. **不是全量覆盖。** 没有独立分母，不能说覆盖了日本全部公演；六家国内乐团中东京爱乐和都响完全没有自动数据。
3. **筛选只是匹配，不是作品库。** 作曲家靠约 120 位的别名表（假名/汉字/拉丁写法），表外作曲家按页面原文子串匹配；作品只对“交响曲/协奏曲/奏鸣曲/四重奏 + 第N番”生成规范键（如 `beethoven:symphony-9`），其余按原文匹配，所以“第九”这类俗称搜不到“交响曲第9番”。读卖、KAJIMOTO、Japan Arts、NHK 的曲目来自各自详情/JSON，但曲目写法不统一，个别行可能被拆错或漏掉；演奏者角色（独奏会演奏者/客演独奏/指挥/其他）是规则推断，二重奏等不升格。
4. **类别需要你判断。** 自动提示只有“钢琴独奏会”和“国内乐团”；海外乐团来日需在确认时手动选类别。
5. **跨来源重复不会自动合并**（同一场可能出现在 Japan Arts 与神奈川艺术协会两处）。待确认页会提示“可能重复”，你可以把没确认的那条标成重复并隐藏（可撤销，见 [ADR-0003](adr/0003-cross-source-duplicate-review.md)）；**两条都已确认的，发现页仍然显示两张卡**。
6. **提醒不会真正发出。** 本地版会排好投递，`classical-radar remind-run` 手动把到点的交给假发送器（只写本地文件，见 [ADR-0002](adr/0002-reminder-scheduling-fake-sender.md)）；没有邮件/推送，没有定时器；线上 Pages 站点只记录订阅，不产生投递。
7. **售票状态不是余票。** “发售中”只表示官方页面如此标注。
8. **改期识别是保守规则**：同一节目下只有一条旧场次和一条新场次对不上时才认定为改期；其余歧义不合并，会出现为“待确认”或标记缺失。
9. **来源政策均未取得自动采集许可**；同步只在你手动运行时发生，没有定时任务。NHK 的季度售票公告 URL 是写死的（`sync.py` 的 `NHK_TICKET_NEWS`），换季需手动更新。
10. 单用户、单令牌、仅本机监听；令牌保存在浏览器 localStorage。没有 HTTPS，不要直接暴露到公网。
11. 无数据库备份机制（SQLite 单文件，自行复制）。
