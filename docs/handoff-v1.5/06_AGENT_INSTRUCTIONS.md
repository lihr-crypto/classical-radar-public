# 06. 首轮执行指令（复制粘贴给 Codex / Claude Code）

你正在开发 Classical Radar 日本古典音乐演出发现与购票管理工具。本次接手 **v1.5**。先阅读 `README.md`、`00_DECISIONS.md`、`03_CONTRACTS.md`、`04_ROADMAP.md`、`02_SOURCES.md`、`05_ACCEPTANCE.md`；其他文档为产品/UI/工具参考。

**重要前提：当前仅完成规划和网页信息调查，没有成功运行的真实自动采集 POC。不要声称采集完成或有全量演出数据。**

## 此轮只做 P0，不开发完整 UI

1. 检查仓库是否已存在、网络/浏览器能力、运行环境与许可。按 `00_DECISIONS.md` 的**七家乐团白名单**开展 POC。不要新增用户已排除的四团。
2. **并行高优先级**验证 Japan Arts、KAJIMOTO、第三个互补官方音乐厅/主办方的海外乐团来日和钢琴独奏会。不能仅先完成七团、把真正困难的发现来源放最后。
3. 逐站检查 robots.txt、使用条款与结构化数据/接口许可；若不确定或禁止则不要运行自动抓取。记录来源政策和替代手段。禁止绕过登录/验证码、限流、访问控制。
4. 先做短时人工 Spike，再用合规的真实网络抓取少量列表、详情、公告，提取演出名称、实际日本场次、曲目、人员角色、官方开票阶段与日期精度。每个字段保留原始出处和上次核验日期，不能靠 LLM 猜时间。
5. 建立可回放的、允许保存的 HTML/JSON fixture；用 `pytest`/CLI 验证纯函数 parser。优先 `httpx + BeautifulSoup`；复杂页面按 POC 决定是否引入 Crawlee/Playwright，勿一次引进全部候选项目。
6. 同时实现最小“官方 URL → 候选字段 → 人工确认 → 入库”的备用通道（尚未确认来源许可不得借此绕过访问限制）。
7. 对每个来源明确人工比对的页面/期间清单及 `采集场次 n / 官方清单总数 N`、关键字段错误条目、售票信息已公布/未公布比例、首次公告日期可得率、更新监控的可行性。**每站8例是机制测试样本，不是95%准确率证明。**
8. 从 `03_CONTRACTS.md` 和 `examples/` 导出共同 Schema/OpenAPI（若出现冲突应先修此文件并记录 ADR），不得使用旧字段 `announced_at`、`date_precision=minute`、`/me/watch` 等。
9. 先用假邮件发送器。没有用户明确授权不得购买云服务、使用收费 API、向真实邮箱发送通知或公开部署。

## 本轮交付清单

- `docs/poc/source-audit.csv`：政策及站点访问记录；7 个国内源 + 3 个海外/独奏候选。
- `docs/poc/p0-report.md`：每源真实结果、n/N、页面/时间范围、公告日期和售票覆盖、阻塞和替代方案；结论 go / conditional / no-go。
- 允许存储的 fixtures、Python 采集器或实验脚本、解析测试与可复现命令。
- 示例规范化 JSON（明确真实与合成区别）、合约一致性检查、错误/失败路径样本。
- P1 建议实际接入的来源清单、开源复用 ADR、剩余风险和用户需决策的问题。

**完成报告格式**：完成事项／实际运行命令与结果／可复现证据／各源阻塞与覆盖／变更文件／Gate 决策／下一轮任务。不得只给 PRD、UI 原型或凭公开网页检索推断“采集已经成功”。
