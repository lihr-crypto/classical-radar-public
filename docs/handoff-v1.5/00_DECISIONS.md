## 0.2 冻结的默认发现设置

- `category=all`：已接入的七家乐团 + 官方确认在日本公演的海外乐团 + 日本或海外钢琴家**独奏会**；不包括全球音乐家百科。
- `months=12`：以服务器在 `Asia/Tokyo` 的请求时刻为基准，未来12个**日历月**滚动；允许选择24个月。
- `region_mode=kanto_first`：东京、神奈川、埼玉、千叶归入优先分区，其余日本地区仍完整展示；切换 `nationwide` 则取消地区优先分区。
- `sort=announcement_desc`：每分区官方首次发布日本场次的可核实日期由新到旧。缺少该日期只能使用**首次官方核实入库时间**排序，并清楚显示“首次收录”，不能伪称“新公布”。
- 地区优先优先于发布时间；同节目多场次显示一张卡，展开所有满足筛选的实际场次。
- 官方来日计划但日期/场馆未定另列“已官宣·待定”；第三方未核实线索只能进入单独低信任区域，并默认不与确认结果混排。

## 0.3 重点保留（不同意 Review 的过度简化）

1. **自动发现必须是主路径**；“粘贴 URL → 提取 → 人工确认”是 P0 备用，不让用户长期手动搜遍全网。
2. **多维结构化筛选保留**：在已收录公演范围内按作曲家、作品、指挥家、演奏者、乐团、音乐厅组合过滤。不做全球作品权威库；第一轮可用规范化原文/少量人工别名 + 全文检索兜底。
3. **三层业务关系保留**：`concert → performance → ticket_phase`；不是过度设计，而是同节目多场与独立售票阶段所必需。
4. **轻量服务端查询保留**：使用 Postgres 普通 LIMIT/OFFSET 起步（小数据），不是强制前端一次性加载所有数据；暂不实现 keyset 游标。
5. **个人购票隐私和基本可靠性保留**：个人状态必须受认证保护；后台任务须防重复发提醒，但不引入复杂分布式消息系统。

## 0.4 已接受 Review 的简化

- 不强制 Supabase；若浏览器通过后端 API 访问，后端做授权即可；只有直连 Supabase 客户端时必须配置 RLS。
- 不在 v1 维护“编辑精选”；UI 可有“值得关注”分组，但只由可解释、低维护规则生成，不能伪造质量排名。
- 首批使用普通服务端分页和单用户体验；不开发复杂组织账号、多人权限管理、微服务。
- 不以每站8例的准确率来宣称 95% 统计表现；测试分为小样本正确性、官方名单覆盖率、连续监测，独立报告。

## 0.5 暂定而非用户确认

当前按“**先私用、未来可迁移至公开服务**”设计；这是技术规划假设，不是用户明确授权公开上线。无许可素材不能公开再发布；私用也不自动免除网站条款和版权限制。付费部署、域名、真实邮件发信、正式共享前须征得用户同意。
