# 04. 执行顺序、工作包与 Go / No-Go

## 第一原则

**先验证最不确定、最影响产品价值的资料链路，而非先把七家乐团界面做漂亮。** 七团和海外/独奏会来源 POC **同一优先级、并行开展**；不把海外发现放到开发最后才碰。

## Stage P0-0（无采集代码前的短时 Spike）

- 审核 Japan Arts、KAJIMOTO、一个互补主办方/音乐厅、NHK、读卖、东京爱乐的网页、条款、公告日期是否存在、开票时刻是否公布、可用结构化接口。
- 输出 `docs/poc/source-audit.csv`（站点、法律/robots、来源 URL、发布日期字段、售票字段、风险与可选替代），明确阻塞项。**手工核对不等于运行成功的采集 POC。**

## Stage P0-A（海外与钢琴独奏会的高风险 POC，优先）

- 先选 Japan Arts / KAJIMOTO / 一家独立的场馆或主办方，做真实网络 list/detail/news/售票的少量合法抓取，制作可回放 fixture。
- 必须分别验证海外乐团日本巡演、**真正的钢琴独奏会**、协奏曲客演误分类、多场地与多渠道售票、日期或售票未公布。
- 做官方链接导入最小通路：候选提取、关键字段人工复核、入库与来源证据；该通路不是最终自动发现替代方案。
- 从官方页面在**确定的期限/类别**内列出人工清单作为覆盖率分母。至少标明哪些公演未能被自动采集及原因。
- Gate A：至少 1 份真实海外乐团公演和 1 份真实钢琴独奏会（存在且合法可用时）能走通来源→结构化→证据；若页面范围无此类样本，标明不满足，不用 mock 冒充；至少 2 个互补官方来源有可维护接入或合法替代方案。

## Stage P0-B（国内七团采集 POC，与 A 并行）

- 使用 `00_DECISIONS.md` 的唯一 7-source 清单。优先 NHK、读卖、东京爱乐验证集中公告/年度日历/多节目类型差异，再扩展剩下四家。
- 所有来源实际审查 robots/条款/允许的访问模式，不允许则只做合法替代；保存允许存储的 fixture + URL + 核对时间。
- 场次、曲目、指挥、独奏者、售票阶段、季度/系列公告关联、变更检测、幂等与来源冲突测试。
- Gate B：七源均有明确审核状态；至少两个差异明显的官方源能从真实网页成功解析 list/detail（其中一个公告来源可被正确关联）；其余有可执行计划与阻塞清单。**不得把初始 POC 的部分覆盖声称七源全量成功。**

## Stage P0-C（先合并合约，后做界面）

- 从 `03_CONTRACTS.md` 派生数据库迁移、Pydantic/TS 类型和 OpenAPI，不另造相似字段。
- 先实现 `concert → performance → ticket_phase`、来源主张、变更日志、`user_pickup` / `user_performance_state` / `reminder_subscription` 的区分。
- 最低数据管线可重跑，处理跨站重复与日期精度；提供采集健康报告与覆盖面板的只读 API。
- Gate C：测试用例满足 `05_ACCEPTANCE.md`，相关字段名称/API 端到端一致。

## Stage P1（基于真正数据的 MVP）

1. 国内七团至少优先上线通过来源验证的子集，并清楚声明当前覆盖；未通过的来源不假装已接入。
2. 同一发现页集成已验证的海外名团/钢琴独奏会数据，缺源时显著显示“覆盖不足”，不是塞全球人物图鉴。
3. 发现页 / 详情 / 多维筛选 / 作品曲目 / 按公演与按主体浏览 / 我的 Pickup / 具体场次状态。
4. 演出/售票/全部日历（月与列表）；明确开启后才发送的邮件节点提醒，变更或取消时重新计划。
5. 单用户认证、来源状态、手动 URL 导入与审计、故障隔离；生产前再确定供应商/部署与合理费用。

**Gate P1**：用户可通过真实、可核实的日本公演完成「发现→了解→Pickup→选场次→看准确票务→（主动开启）提醒」，而非模拟演出。七团中未通过来源验证的部分应明确标示 backlog，不得假称全部覆盖。

## Stage P2（可选增强）

- 扩充**海外来日与钢琴独奏会**的互补官方来源，提升覆盖率。
- 合法试听与介绍、日中姓名别名增强、青年票、ICS 订阅、Push、真实使用后 UI 精调。
- 编辑精选（可解释、人工维护有实际需求时才做），摇滚/爵士后期。

## 开源组件验证清单（只选必要者）

- `changedetection.io`：验证与原生字段 diff 是否重复，若无显著收益不部署。
- `Crawlee Python`：只有多层翻页、重试或 JS 请求复杂时采用；普通静态页先 `httpx + BS4`。
- `Crawl4AI`：复杂未结构化公告候选抽取，不负责判定售票日期真实性。
- `FullCalendar Vue`：首选 UI 组件，检查免费功能与项目许可。
- `Apprise`：多渠道通知扩展候选；首版单一邮件适配器可能更轻。
- `RSSHub/Huginn/Showbook/urlwatch`：参考或替代，不因高 Star 强制加依赖。

## Agent 每轮必须交付

代码、可重跑命令、测试报告、官方真实样本出处/日期、法规/条款检查、不能解决的问题、下一轮优先级。没有真实网络访问时必须明确“blocked”，不要只用示例 JSON 冒充验证成功；不要自行购买云服务或发送真实邮件。
